## 1. Detection Logic in Plain Language
Detects successful `execve` system calls (`syscall=59`, `success=yes`) where `audit.exe` is `/usr/bin/crontab` on Linux hosts monitored by `auditd`.

## 2. Expected False Positives
- Authorized Linux administrator editing scheduled maintenance jobs during a change window.

## 3. Verification Tests (Attack & Benign)
- **Attack Trigger Command:**
  ```text
  echo "* * * * * echo hi" | crontab -
  ```
- **Benign Activity Test (Must NOT Fire):**
  ```text
  ls -la /etc/cron.daily (reads directory metadata without invoking `/usr/bin/crontab`).
  ```

## 4. L1 Analyst Triage Steps
1. Identify the acting user via `data.audit.auid` (login UID) and `data.audit.uid` (effective UID).
2. Inspect `data.audit.execve` arguments (`a0`, `a1`, `a2`) and check `/var/spool/cron/crontabs/<user>` on the host to view the exact scheduled command.
3. Verify whether the session originated from an anomalous SSH login or after an `authorized_keys` modification (`100202`).
4. If unauthorized, capture `/var/spool/cron/crontabs/<user>` as evidence, hash it, and remove the malicious cron entry.

## 5. Escalation Path
- Escalate to L2 within 1 hour (P3), or upgrade to P2 if the cron job executes a reverse shell or payload from `/tmp`/`/dev/shm`.
- **Six-Field Escalation Call Required:** *Who, What, When, Where, Evidence, Need.*
